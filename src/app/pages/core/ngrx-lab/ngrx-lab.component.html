NgRx · shared state

NgRx is a library for managing application state — not a shopping-cart product. The word Store here means a state container (Redux vocabulary): a single place that holds data many parts of the app can read and update through a clear flow. You dispatch actions (events), a reducer returns new state, and selectors expose slices to the UI. @ngrx/signals (SignalStore) is the modern, less-boilerplate path — same job. Local UI still belongs in signals; a tiny shared counter still belongs in a service.

Start here — state, not “a store”

Why NgRx at all? When distant screens need the same data — auth session, feature flags, filters, a notification list, or yes, a cart — prop-drilling inputs/outputs gets noisy. You want one source of truth and a predictable update path: the view never patches state in place; it asks, by dispatching.

Naming trap: In NgRx docs, “Store” ≠ retail store. It means where the state lives. The snack cart below is only a demo domain (a list of items + qty + async load). The same pattern applies to todos, selected rows, or user preferences.

Side work (HTTP, timers) lives in an effect: it hears an action, does the async job, then dispatches a success / failure action. The reducer stays a pure function of (state, action) → newState.

Use Skip
Component signals Toggle, form draft, local UI State many routes must share
Service + signals Small shared state (this lab’s CounterService) Many features, time-travel, interceptable events
NgRx Store Shared domain state (auth, filters, collections…), complex flows, DevTools A single page’s checkbox
SignalStore New NgRx code — less boilerplate, signal-first You already have a large action/reducer graph to extend
